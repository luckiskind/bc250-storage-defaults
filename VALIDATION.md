# Validation and limits

## Measured on one BC-250

Hardware: PNY CS2241 1TB, PCIe 5 GT/s x2; CachyOS kernel `7.2.8-1.219-cachyos-bore-bc250`; Btrfs zstd:1. The link itself remains hardware limited. Compression can increase logical bytes delivered per second by reducing bytes crossing that link; incompressible data remains limited to approximately 790 MB/s.

After 2.5 seconds idle, the tested drive's first 4 KiB read took approximately 21–22 ms with its original 100000 us tolerance and 1.75–2.27 ms with 5000 us. These are controlled idle/read measurements, not a count of sleep events during gameplay. Actual suspend/resume and reboot behavior of the packaged release remain untested; the original installed service was tested with stop/start.

A clean filesystem matrix compared nine representations, six read workloads and three repetitions: 486 read runs, plus 216 later CPU wake-policy checks. Earlier exploratory timings overlapped a CPU latency test and are excluded. The data set was 29 copied ELF files, approximately 2 GiB, plus an incompressible control. Content hashes were verified.

Native 16 KiB zstd:1 Btrfs repacking versus the original zstd:1 layout gave these median throughput changes on that corpus:

| Workload | Change |
| --- | ---: |
| Sequential, 1 thread | +13.2% |
| Sequential, 4 threads | +16.6% |
| Random 4 KiB, 1 thread | +53.7% |
| Random 4 KiB, 4 threads | +27.0% |
| Random 64 KiB, 1 thread | +34.7% |
| Random 64 KiB, 4 threads | +15.2% |

Sequential logical throughput reached about 1195–1225 MB/s. The incompressible control did not gain. Smaller compressed extents reduce random-read decompression amplification but may reduce compression efficiency and increase metadata. These results do not establish improvements for every application, game asset archive, filesystem or SSD. Queue/scheduler experiments found no broad validated improvement, so those changes are not packaged.

The earlier persistent lab deployment verified 211 files (1,072,514,930 logical bytes) before this reusable packaging work. That deployment history is separate from the tests below. The source retains the same defrag operation, power target, scheduling policy and eligibility limits, with portable installation and disposable validation replacing personal lab paths.

## Original v0.1.0 packaged source checks

- 15 isolated Linux tests cover repeat apply/undo, existing file preservation, administrator edits, unknown manifest paths, failed activation cleanup, keeping helpers if stopping fails, simulated controller reset, power-policy conflicts, unsupported drive refusal, hash-mismatch STOP handling, deadline bounds and file-class exclusions.
- Read-only compatibility check passed on the BC-250.
- The shipped self-test passed on the BC-250: it repacked a newly created 2 MiB private fixture, verified SHA-256 `e45d63f8863fb93f739ffd798351ddaca397bd7142c73e5fc02a1641084e29c5`, and reported maximum compressed extent size 16384 bytes. It removed the fixture afterward. The installer runs this before enabling any service. Systemd unit verification also passed.
- Installer/undo tests mock systemd and use temporary files. They do not uninstall or replace the already deployed lab defaults. A fresh complete installation in a second clean OS is not yet qualified.
- CI checks Python/shell syntax, isolated tests and whether the exported add-only source patch applies cleanly. CI does not claim real NVMe or Btrfs performance testing.

Run isolated checks on Linux:

```sh
python3 -m unittest discover -s tests -v
python3 tests/live_check.py /path/to/writable/btrfs/scratch
```

The live check changes only its disposable fixture. It does not alter services, real program files, power settings or the existing maintenance state. Keep performance validation separate from ordinary CI; virtual/cloud disks do not reproduce the target link or NVMe sleep states.

## Stage 0 development qualification

The initial goal audit found a real maintenance failure after a content-verified file retained a 32 KiB encoded extent. The same class of residual extent was reproduced on a disposable installation fixture. The development worker adds one bounded per-range-fsync retry, explicit content-verified layout-miss reporting and durable budget reservations before mutation. It does not claim to have established the precise kernel scheduling cause.

The expanded suite passes **109 isolated Linux tests**, including partial-write cleanup, existing-destination preservation, retry byte limits, residual-layout reporting, durable crash-budget accounting, transaction locking, recovery ownership checks and disposable-OS/image guards. A bubblewrap user-namespace integration run also passes fresh apply, repeated apply, stop/start restoration, a simulated controller reset and the actual resume hook, administrator-edit refusal, repeated undo, failed-enable cleanup and reinstall. Real Btrfs ioctls and installer file operations run against private fixtures; service control and NVMe sysfs are simulated.

A separate [40-case SIGKILL matrix](docs/evidence/stage0-installer-crash-tests.json) passes interruption during partial staging, each staged/published file, validation/activation, manifest commit, staged cleanup, service shutdown and each removal. Recovery is checked twice for idempotence. A same-content administrator replacement with a different inode is preserved. These are process-interruption results on real Btrfs with simulated services/controller state; they do not establish device power-loss durability.

The [native data baseline manifest](docs/evidence/stage0-native-baseline-manifest.json) records three independent copies of four public ELF libraries plus a 32 MiB incompressible control. All 15 files matched their reference content hashes and had no FIEMAP shared extents. B0/B1 used ordinary native writes, with maximum compressed extents of 128 KiB where compression occurred; all four repacked B2 ELF copies reached 16 KiB. The control remained uncompressed. The builder did not change power settings or source files. No throughput comparison was performed on these new copies, and they are not full-system/independent-volume baselines.

A fresh Arch userspace with Python 3.14.8 and systemd 262.1 passes [11 real-systemd lifecycle checks](docs/evidence/stage0-real-systemd-result.json): apply/repeat apply, active services, stop/start restoration, simulated reset/resume hook, a bounded real worker pass, undo/repeat undo/reinstall, guest reboot/startup reapplication and undo after reboot. The worker verified 6,344,456 fixture bytes, submitted 98,304 retry bytes and charged 6,442,760 bytes within its 16 MiB test budget. The run took about 10.6 seconds; this is test duration, not a throughput result. A prior lab prototype also passed; the recorded evidence comes from the reusable harness on a separately prepared fresh tree.

This test uses real systemd as guest PID 1 and real Btrfs, with a distinct user namespace, simulated NVMe controls, private qualification networking, 1 GiB memory and a two-CPU quota. It shares the host kernel and volume. Host power/timer services remained active at 5000 us. The initial ID-mapped attempt refused Btrfs defrag with EPERM and rolled back; shifting only guest file ownership resolved the environment limitation. See [the reproducible qualification guide](docs/real-systemd-qualification.md).

The [separate-kernel virtual recovery test](docs/evidence/stage0-virtual-recovery-result.json) passes three boots: initial reference verification and committed state, persistence after orderly restart, and reset through a new overlay. QEMU 11.1.2 boots stock Linux `7.2.11-arch1-1` on a separate Btrfs image with real systemd. The protected raw baseline's sparse fingerprint is unchanged, and the guest/host workspace filesystem UUIDs differ. The recipe is documented in [the virtual recovery guide](docs/virtual-recovery.md). These layered, CPU-emulated tests do not measure native performance or qualify physical boot/power-loss behavior. Storage-profile activation under whole-guest interruption is not tested by this boot-only probe.

The subsequent [seven-case profile fault suite](docs/evidence/stage0-virtual-profile-faults.json) passes eight acknowledged whole-guest interruptions and 15 boots, including interrupted recovery and an explicit missing-timer-link compatibility injection. It exposed a committed-manifest/missing-startup-directory failure in the previous installer. The repaired installer synchronizes service-link directories before commit/completed shutdown and reestablishes committed activation during recovery after checking ownership. The fixed ordinary commit case verifies startup services before recovery, so recovery cannot hide a persistence failure. A [fresh 40-case process interruption run](docs/evidence/stage0-service-link-process-crashes.json) also passes. See [the fault recipe and limits](docs/virtual-profile-faults.md). Guest RAM/kernel loss is tested; physical volatile drive-cache loss and interrupted worker repacking remain unqualified.

After backing up the installed lab worker, manifest and SQLite ledger, the tested worker repair was applied on the BC-250. A normal bounded pass completed successfully: 104 files met the content/layout checks, 536,367,504 logical bytes were processed, 425,984 retry bytes were submitted, and total charged work was 536,793,488 bytes, below 512 MiB. The timer was restored and the 5000 us drive policy remained active. Installed file hashes matched the updated manifest.

The [calibrated volatile-cache lab](docs/volatile-cache-faults.md) adds four independent QEMU-client durability scenarios and [one installer VM write-loss case](docs/evidence/stage0-cache-installer-vm.json). The accepted VM cut discarded 102,400 pending model bytes, then recovery passed twice and orderly shutdown left zero pending writes. Matching calibration/package/runtime hashes, baseline preservation and unchanged actual host policy verified. The initial zero-dirty-byte exploration is excluded from write-loss qualification. Neither this software model nor its green checks establish physical SSD power-loss behavior or interrupted-worker coverage.

The [worker VM matrix](docs/evidence/stage0-worker-cache-vm.json) adds a baseline and three positive cache-loss cuts across seven boots. The real 6,344,456-byte ELF fixture preserves content/metadata and reaches 16 KiB extents. Reservation, range-processing and pre-final-charge cuts discard 48, 108 and 48 KiB respectively; full uncertain reservations survive and repeated recovery consumes no additional budget. The worker now explicitly verifies SQLite EXTRA synchronization and supported journal modes, and synchronizes its state-directory parent before authorizing mutations. A [fresh installation crash rerun](docs/evidence/stage0-worker-ledger-process-crashes.json) and [backed-up live repair](docs/evidence/stage0-worker-ledger-live.json) verify compatibility and preservation of old charges/configuration. The host's successful zero-work pass respects its already-nearly-exhausted daily allowance. See [the worker guide and limits](docs/worker-cache-recovery.md).

The [persistent-ownership repair](docs/persistent-ownership.md) fixes a reproduced refusal after an unchanged Btrfs filesystem receives a different device number. New version 2 journals pair the full filesystem UUID with an opaque Linux export handle. A seven-case native matrix checks three completed recovery paths and four strict refusals, with original contents/witnesses/journals preserved before any service action. The latest 88-test suite, fresh integration and [40-case process matrix](docs/evidence/stage0-persistent-ownership-process-crashes.json) pass. Legacy journals retain their strict original identity checks and are not automatically upgraded from contents. A rebuilt [selected installer cache-loss VM case](docs/evidence/stage0-persistent-ownership-cache-vm.json) passes after 32 KiB of pending model writes are discarded, guest termination and repeated recovery, with matching source/calibration hashes and preserved baseline. The live helper/power configuration is unchanged by this installer-only repair.

The [native-volume baseline set](docs/evidence/stage0-native-volume-baselines.json) now adds three distinct Btrfs filesystems with identical checked contents/metadata: 36,650 durable entries and 694,670,218 logical file bytes each. The B2 worker executes natively on the actual CachyOS kernel in verified private user/network namespaces; 46 files verify, with 142,885,416 logical bytes charged and no retry bytes, within the unchanged pass allowance. All regular-file extents are checked for sharing, and outer image extents are neither shared nor compressed. Completed images are read-only and the source OS/power policy remain unchanged. These are loop-backed userspace volumes, not physical boot or benchmark results. See [construction, ownership and remaining qualification](docs/native-volumes.md).

The [native startup/reset matrix](docs/evidence/stage0-native-trials.json) now passes nine guest-systemd launches on the actual BC-250 kernel. Three variants retain a file mutation and SQLite count through orderly shutdown/remount/relaunch, then a fresh independent copy restores each original tree and starts with a new nonce. Every probe reaches the usable target with zero failed guest units; protected baseline fingerprints are unchanged. The startup audit also found historical lab services pointing to uncopied scripts in the first construction set. The corrected builder strips only the exact known fixtures from new copies and preserves edited/unfamiliar units. The [clean baseline set](docs/evidence/stage0-native-clean-volume-baselines.json) has 36,646 durable entries and 694,669,717 logical file bytes per tree. Its B2 pass verifies 45 files and charges 141,427,840 logical bytes. See [the native trial recipe and limits](docs/native-trials.md). Earlier construction reports retain their own source versions and do not imply startup qualification.

The [private-workspace provenance qualification](docs/workspace-provenance.md) adds six real Btrfs migration/remount/replacement checks, two guarded migrations of existing lab trees and one fresh seed/private-user probe. New markers use persistent Btrfs identities for both workspace and guest; old records can migrate only while their original device/inode check still matches and their private seed authenticates. An incomplete earlier build lacking that ownership record was refused and preserved. Physical boot preparation preserves verified boot files on the BC-250 and Windows PC plus a same-SSD read-only root reference; it has not established an independently booted recovery environment.

These are reliability and native startup/reset results, not a new performance comparison or physical boot/resume qualification. Actual host reboot/resume, hard power-loss recovery, independently restored full-system baselines and qualification on another clean OS are still open Stage 0 work. See [the baseline and recovery record](docs/baseline.md).
